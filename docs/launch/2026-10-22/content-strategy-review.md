# AGYNEXA content strategy and Humanizer review

**Scope:** Planning reference for the eight editable program-page families, ten implementation services, and nine solution entries listed in `copy-input.json`. This is an editorial plan, not a rewrite or an SEO forecast. Page and query labels below are **hypotheses, unmeasured**; Semrush had no API units and Exa was exhausted. The inventory contains no measured search volume, conversion, or buyer evidence.

**Guardrails for execution:** Keep the approved name, colors, and visual identity. Text and section order may change inside the existing templates. Preserve English/Arabic route parity. Leave the homepage/opening screen, Hero, and video untouched. Explain offers as scoped implementation work, since most service pages describe engagements. Do not imply a feature is live unless the current product actually provides it. The current app has two small templates (KnowledgeGrid and ServiceFlow), private owner-only workspaces, short pasted/TXT/MD sources, cited lexical retrieval, chat in an agent, an internal human-reviewed support proposal, approved public widget sources, and run history. It has no billing, CRM, ERP, helpdesk, EHR, OSS/BSS, PDF/OCR, or semantic-search integration. A saved private brief is not delivered to AGYNEXA.

## Three representative before/after examples

**Service: Enterprise knowledge**

Before: “Search returns documents without resolving the question, while generated answers can miss policy changes or access rules.”

After: “Staff may find a document without finding the current answer. We can scope a search workflow that uses approved sources, cites the source it used, and sends unanswered questions to a person.”

Truth boundary: this describes an implementation scope. The current app supports short pasted text/TXT/MD and cited lexical retrieval; connectors, large repositories, semantic search and automatic updates are not live capabilities.

**Solution: Customer operations**

Before: “A service question, change request and complaint need different review paths.”

After: “A question about a policy, a request to change an account, and a complaint need different next steps. A scoped assistant can prepare an answer, ask for missing details, or send a summary to the right staff reviewer.”

Truth boundary: “send a summary” means prepare a handoff within the agreed workflow. Do not imply an external system or AGYNEXA inbox receives it unless that path is built and verified.

**Industry: banking**

Before: “Assist service staff with policy retrieval, document review and reconciliation exceptions.”

After: “A possible bank workflow is to help staff find the current complaint procedure, list information missing from a case, and prepare a summary for review. Bank employees decide how to classify, resolve and report the complaint.”

Truth boundary: mark this as a proposed example, not a deployed bank project. Keep private account or complaint records out of the public widget. No financial decision or regulatory filing is automated.

## Copy execution checklist

- **Page structure:** plain heading answers the visitor’s question; opening paragraph names audience, problem and outcome; technical terms are explained; section order follows customer task then details; examples are labeled as proposed scopes where appropriate.
- **Capability truth:** distinguish current app features from proposed implementation; disclose file types/limits where relevant; label vendor connections as candidates pending account/API/permission checks; never promise PDF/OCR, CRM/ERP/helpdesk/EHR/telephony integration, semantic retrieval, automatic updates, billing, or external delivery before verified support exists.
- **Approval and safety:** name what a person reviews or decides; keep healthcare clinical decisions, financial transactions, coverage/claims outcomes, account changes and energy safety-critical actions with authorized people; show when the assistant lacks evidence and escalates.
- **Chat-first journey:** prompt for the business task before inviting company files; clarify scope and intended output; draft the brief; explain optional source addition; distinguish saved private brief, pending internal human review, and actual delivery. Never expose private workspace content through public routes/widget.
- **Forms:** labels, helper text, required/optional state, upload type/size, privacy notice and consent are explicit; preserve input after recoverable errors; do not request sensitive data before needed; specify what submission does in runtime-truthful terms.
- **Validation and states:** write clear invalid-input, unsupported-file, size-limit, missing-source, permission-denied, save-failed, retry, success, empty, loading, timeout and provider-error messages. State the next action and whether entered content remains saved.
- **Chat capabilities:** distinguish sourced answers from drafts and proposals; cite available source material; explain no-answer behavior; show review status; avoid saying an external action ran without a confirmed receipt.
- **Navigation and metadata:** use terms customers search for in page title, meta description and headings where they accurately fit; one clear topic per page; bilingual titles/descriptions are natural equivalents; accurate canonical/hreflang/locale labels; no keyword repetition or promises of ranking.
- **EN/AR parity:** same audience, deliverable, caveat, CTA and privacy meaning; use clear Modern Standard Arabic, natural and direct; preserve names and technical identifiers where necessary; check RTL layout, punctuation, form errors, empty/loading states and menu labels.
- **Proof and review:** no invented testimonials, customer counts, market volumes, CPC, ROI or guarantees; have a domain reviewer validate regulated claims, a bilingual reviewer check Arabic, and a product owner verify every capability statement against the actual runtime.
