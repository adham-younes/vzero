# Page ownership and search intent

Editorial plan only. The inventory is based on the current route-generation source: 34 canonical public page subjects per language, covering 68 English/Arabic URLs. The `/services/solutions` alias is a redirect, not a separate content page. No routes are created or changed here.

Search phrases below are research hypotheses and terminology, not measured keyword volumes, difficulty scores or ranking forecasts. English and Arabic columns describe equivalent needs without requiring literal translations.

## Page hierarchy

The home page establishes the platform category and audience. Capabilities explain how the platform works. Solutions explain how capabilities combine into a business workflow. Industries put those workflows into an operating context. Architecture and security provide technical depth. Getting started explains the real entry path. Contact remains a contact action.

The current `/services` URLs can remain stable while their editorial role becomes platform capabilities. Renaming visible navigation is a later implementation decision; it is not done by this plan. Each detailed page gets its own main question, explanatory sequence, example and next step.

The current site has one industries route with ten sector sections. All ten need independent content briefs and specific workflows. Their full structure is in [the sector map](INDUSTRY-PROBLEM-SOLUTION-MAP.md). A later route proposal can turn a sector into a dedicated page when enough unique, supportable content exists. ## Customer journey and action wording

The public journey is: understand the product → see how building works → identify a relevant capability or sector workflow → understand data and authority requirements → take the actual supported entry action. Technical buyers can branch into architecture, integration and security without being sent back to a generic brief.

Remove the requested phrases “Watch a working example” and “Discuss your workflow” from the new draft. Educational links should name their destination, such as the platform explanation or orchestration page. An action that opens sign-in should say so. A contact action must explain how contact occurs. A save action must state where the record is saved. No label may turn a manual handoff into a submission receipt.

Authenticated Studio, billing and account flows are not redesigned in this content phase. Public entry copy must still match what those flows actually do.

## SEO and language acceptance

- Assign one principal question to each page. Use natural related terms where they explain the topic; do not impose keyword density or duplicate synonyms in headings.
- Each language receives its own title, description, H1, paragraph structure, FAQ selection and link wording. Match factual scope and action meaning, not sentence order or length.
- Preserve distinct language URLs and reciprocal language links. Canonicals, language annotations and structured data are implementation checks for a later approved site change, not changes made here.
- Use plain answers to real user questions. No manufactured reviews, organization size, case studies, performance numbers or FAQ rich-result promises.
- No ranking or AI-answer inclusion guarantee. No special AI text file is treated as a substitute for useful visible content.

These principles follow Google's guidance on [helpful original content](https://developers.google.com/search/docs/fundamentals/creating-helpful-content), [multilingual URLs and language signals](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites), and [AI features in Search](https://developers.google.com/search/docs/appearance/ai-features). The current planning work does not measure search demand or diagnose the site's actual rankings.
