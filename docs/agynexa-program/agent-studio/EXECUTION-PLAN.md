# تكليف Agent Studio المعتمد

ورد في 20 أكتوبر 2026. النص التالي هو التكليف فقط، دون بقايا تصدير المتصفح الملحقة بالمرفق. التنفيذ المفوض الآن: المرحلة A ثم التوقف.

AGYNEXA — تحديث موجّه وبناء Agent Studio على مراحل
الهدف والنطاق
حوّل الأساس الحالي إلى منتج يستطيع العميل من خلاله إنشاء وكيل محفوظ، إضافة معرفة، تشغيله، نشر إصدار منه واستخدامه. ابدأ بقالب KnowledgeGrid وقالب ServiceFlow محدود فوق محرك واحد؛ لا تبنِ الخدمات العشر دفعة واحدة، ولا تعتبر صفحاتها منتجات تشغيلية.

هذا تكليف جديد يضاف إلى العمل السابق، وليس إعادة تنفيذ لمراحل الموقع 0–6. اعتمد تقرير التدقيق المرفق، ثم افحص التغييرات التي حدثت بعده فقط. لا تعِد زحف Kore.ai أو كتابة المحتوى أو إعادة تصميم المنصة.
قواعد التنفيذ والحماية
- اعمل على مشروع vzero المرتبط بـ vzero-nine-beryl.vercel.app بعد إثبات المستودع والفرع والربط الحالي. لا تعمل على مشروع Adham-AI-Agent- المنفصل. لا تمس الموقع الأساسي agynexa.si.
- اعمل على فرع مستقل؛ لا تدفع إلى main ولا تدمج ولا تنشر Production. قد يؤدي الدمج نفسه إلى نشر تلقائي، فلا تعتبره إجراءً محليًا.
- حافظ على الحسابات والموجزات والمحتوى والمسارات العربية والإنجليزية وSEO. التغييرات إضافية ومحددة، بلا ترقية جماعية للتبعيات أو تبديل framework.
- استخدم بيئة بيانات معزولة للتطوير. جهّز migrations للمراجعة؛ لا تطبقها على قاعدة قائمة أو تغيّر إعدادات Auth الحية دون موافقة مستقلة تحدد المشروع والإجراء. لا تشترِ موارد جديدة تلقائيًا. عند غياب بيئة معزولة، استخدم بيئة محلية مناسبة أو توقف عن الجزء المحتاج إليها فقط.
- Groq المدفوع مفوض للاختبارات الوظيفية وتشغيل النماذج المطلوبة باستخدام المفتاح الموجود خادميًا. لا تكشف الأسرار، ولا تطبعها في logs، ولا تضعها في NEXT_PUBLIC_* أو المستودع.
- افحص الأدوات والمهارات المتاحة داخل جلسة Codex. استخدم karpathy-guidelines وHumanizer إن وُجدتا، ومهارات Supabase وVercel ذات الصلة فقط. استخدم أدوات التصميم للضبط لا لاستبدال القالب. لا تفترض اتصال أداة لأن ChatGPT استخدمها سابقًا.
- احتفظ بنظام التصميم الحالي: الأسود والأخضر، الخطوط، الأزرار، البطاقات، الحالات والمسافات وRTL/LTR. حلّ aliases الفعلية قبل تعديل المكونات، خصوصًا Button؛ لا تعدّل نسخة غير مستخدمة.
- لا تنشر ادعاءات عن وظائف غير منفذة، ولا تضف لغة «نتعلم/مشروع تجريبي» إلى التسويق. حالات عدم الجاهزية تبقى صريحة في تقارير التنفيذ ولا تتحول إلى ادعاءات جاهزية.
1. المقدمة والفيديو: إصلاح محدود لا إعادة تصميم
شكوى المالك الحالية هي انخفاض إضاءة الفيديو بعد تعديلات ألوان الخطوط والعنوان. تعامل مع السبب كفرضية تحتاج فحصًا، لا حقيقة محسومة.
1. اكتشف المسارات الفعلية لـ background.mp4 ومكوّني landing-5-hero-video وlanding-5-hero-section. احفظ بصماتها ولقطات الوضع الحالي قبل العمل.
2. افحص computed styles وسلسلة العناصر الأب وطبقات ::before/::after وoverlay وopacity وfilter وbackdrop-filter وmix-blend-mode وz-index، مع diff التغييرات ذات الصلة فقط.
3. قارن بنفس توقيت الفيديو ونفس حجم الشاشة، حتى لا تخلط اختلاف إطاراته مع اختلاف الإضاءة. راجع مرجعًا بصريًا معتمدًا إن وجد؛ لا تفترض أن كل لقطة قديمة مقبولة.
4. صحح أقل قاعدة CSS مسؤولة عن التعتيم الزائد، وقيّد التصحيح داخل Hero. لا تضف brightness مبالغًا فيه لإخفاء السبب، ولا تستبدل ملف الفيديو أو تعيد ضغطه.
5. لا تغيّر نص العنوان أو ألوانه أو الخط أو حجمه أو موضعه أو CTA بحجة تحسين التباين. لا تغيّر playback أو crop أو object-fit أو ارتفاع المقدمة. إن تعارض وضوح النص مع إصلاح الإضاءة، اعرض بديلًا محدودًا لاعتماد المالك بدل تغييره تلقائيًا.
6. اجعل إصلاح Hero في commit مستقل قابل للتراجع. سلّم مقارنة قبل/بعد؛ وعند اعتماد الشكل اقفل النتيجة baseline جديدة. لا تعد للمقدمة أثناء بناء Studio.
2. إنشاء الحساب والدخول بدون رسائل بريد
قرار المالك: لا رسالة تأكيد، ولا OTP بريدي، ولا magic link، ولا رسالة ترحيب عند التسجيل أو الدخول. لا تُرسل رسائل باسم Supabase.
- حافظ على مسار البريد وكلمة المرور العامل، بعد فحصه، ولا تستبدل Supabase Auth أو تنشئ نظام كلمات مرور خاصًا.
- لا تعِد تفعيل تأكيد البريد كحل تلقائي لملاحظة التدقيق. راجع إعدادات التأكيد والإشعارات ومسارات الإرسال المباشر، وليس واجهة الموقع وحدها. لا تغيّر الإعدادات الحية دون التفويض المحدد أعلاه.
- ميّز بين جلسة مستخدم موثقة وملكية صندوق بريده. email_confirm:true أو تاريخ التأكيد الناتج عن autoconfirm ليس دليلًا مستقلًا على امتلاك البريد.
- اعتمد user_id الموثق وعضوية مساحة العمل في الصلاحيات. لا تمنح عضوية أو دورًا أو وصولًا بسبب تطابق البريد أو نطاق الشركة.
- لا تفعل دمج حسابات أو ربط OAuth تلقائيًا مع الحسابات المؤكدة إداريًا. إضافة Google/Microsoft ليست شرطًا لهذه المرحلة؛ تحتاج فحص خطر ربط الهوية واعتماد إعداداتها قبل التفعيل.
- احفظ مصدر إثبات الهوية في بيانات خادمية لا يستطيع المستخدم تعديلها عند الحاجة. لا تستخدم user_metadata القابل للتعديل لمنح أدوار أو إثبات بريد.
- احتفظ بحماية محاولات الدخول، ورسائل أخطاء لا تكشف الحسابات، وفحص الجلسات والصلاحيات وحماية الطلبات المغيرة للحالة. لا توسع استخدام المفتاح الإداري لتجاوز RLS.
- افصل استعادة الحساب عن التسجيل. لا تشغل resetPasswordForEmail بالمرسل الافتراضي، ولا تعرض نجاح إرسال وهميًا، ولا تعيد تعيين كلمة المرور لمن يعرف البريد فقط.
- قبل إتاحة الاستخدام التجاري العام، حدّد مسار استعادة حقيقيًا: هوية موثوقة أو وسيلة استعادة أصلية يدعمها المزود، أو بريد AGYNEXA مخصص يطلبه المستخدم بعد اعتماد إعداده. لا تخترع بروتوكول استعادة خاصًا. ما لم يُعتمد ويُختبر مسار، سجّل الاستعادة عائق إطلاق واضحًا دون تعطيل التطوير الداخلي.
- إعداد SMTP بعلامتنا التجارية خيار لاحق منفصل؛ لا تشغله ولا ترسل بريد اختبار للعميل في هذا التكليف. لا تَعِد بأن تغيير اسم المرسل وحده يغيّر النطاق والروابط وكل ما يراه المستلم.
3. Groq والنماذج: تشغيل حقيقي قابل للقياس
متغير السر الموجود: GROQ_API_KEY، خادمي فقط.

النموذج الأساسي المقترح:
openai/gpt-oss-120b

النموذج الثاني المطلوب تقييمه:
qwen/qwen3.8-27b

لا تستخدم الاسم المختصر qwen3.8-27b كمعرف API، ولا تفترض أن النموذجين متاحان للحساب بمجرد وجود المفتاح.
- نفذ فحصًا واحدًا لـ GET https://api.groq.com/openai/v1/models ثم طلبًا فعليًا صغيرًا لكل نموذج. احفظ نتيجة الوصول والميزات دون المفاتيح أو بيانات خاصة. قائمة النماذج وحدها لا تثبت صلاحية كل ميزة.
- راجع الوثائق الحالية وحالة Production/Preview. عند إعداد التكليف كان GPT-OSS-120B مدرجًا ضمن Production وQwen3.8-27B ضمن Preview. اجعل الأول افتراضي التشغيل العام، والثاني للتقييم الداخلي ما دام Preview؛ لا تجعله اعتمادًا إنتاجيًا أو fallback تلقائيًا بلا مراجعة واعتماد.
- أنشئ capability registry صغيرة: model ID، النص/الصورة، tool calling، structured outputs، reasoning، حدود السياق والمخرجات، availability. تحقق من تقاطع الميزات لا وجود كل ميزة منفردة فقط.
- لا تمرر المعاملات نفسها عميانيًا للنموذجين. تحقّق من reasoning_effort والقيم المدعومة وإعدادات streaming والـSDK.
- وفق التوثيق الحالي، Structured Outputs لا يجتمع مع streaming أو tool use في الطلب نفسه. افصل طلب توليد الإعدادات المنظمة، وطلبات الأدوات، وبث إجابة المحادثة. أعد التحقق عند التنفيذ؛ لا تحل خطأ API بحذف التحقق من البنية.
- افحص JSON الناتج بـZod أو أداة التحقق الموجودة. نجاح schema لا يثبت صحة المعلومة أو جواز تنفيذ الإجراء.
- وفّر اختيار نموذج مسموح للمسؤول، مع إعدادات محفوظة لكل وكيل. الجودة أولًا؛ استخدم تفكيرًا أعلى للمهمة المعقدة، لا استدعاء النموذجين لكل رسالة بلا سبب.
- عند 429 احترم Retry-After وحدود المؤسسة، مع backoff ومحاولات محدودة. لا تفترض أن التحويل لنموذج آخر بنفس المؤسسة يلغي حدودها. فرّق بين أخطاء الصلاحية والفاتورة والسعة والإدخال غير المدعوم.
- لا تسقط صورًا أو سياقًا أو أدوات بصمت أثناء fallback. لا تخترع ردًا ناجحًا عند فشل المزود.
- سجل model وtokens وlatency وrequest ID والأخطاء والتكلفة التقديرية بمصدر تسعير وتاريخ. لا تخزن reasoning الخام أو الأسرار في سجلات العميل.
- لا تفرض حصة مجانية صغيرة أو سقف إنفاق اعتباطيًا على المالك. الاشتراك المدفوع لا يزيل حدود المزود أو ضرورة سقف خطوات الوكيل، مهلة التنفيذ، حد التزامن، الإلغاء ومكافحة الإساءة. اجعلها إعدادات خادمية قابلة للضبط؛ لا تسمح بحلقات لا نهائية.
- حصة Groq لتشغيل التطبيق منفصلة عن حصة Codex. استمر في تقليل إعادة البحث والاختبارات غير الضرورية داخل Codex.
4. شكل المنتج المطلوب
أنشئ مساحة Agent Studio داخل المشروع الحالي، بمسارات واضحة مثل /studio و/ar/studio بحسب Router الموجود، دون تكرار تعارض catch-all. اجعل الصفحات الخاصة noindex وغير قابلة للتخزين المشترك بين المستخدمين.

الرحلة الملزمة:
تسجيل/دخول بلا بريد → مساحة عمل → إنشاء وكيل من قالب → إعداداته ومعرفته → اختبار فعلي → حفظ إصدار → نشر → استخدام عبر API أو widget → مراجعة المحادثات والاستهلاك → إيقاف أو تحديث.

الواجهة تتضمن: قائمة الوكلاء، إنشاء وكيل، التعليمات واللغة والنموذج، مصادر المعرفة وحالتها، الأدوات المسموحة، المحادثة الاختبارية، الإصدارات والنشر، وسجل التشغيل والاستهلاك.

ابدأ بمساحة ذات مالك واحد، مع نموذج عضويات قابل للتوسع، دون دعوات فرق أو ربط مؤسسات بالبريد الآن. أنشئ مساحة العمل idempotently ولا تنقل الموجزات القديمة جماعيًا؛ حافظ على ملكيتها الأصلية.

القالبان الأولان:
- KnowledgeGrid: مساعد معرفة من مصادر مساحة العمل، بإجابات واستشهادات فعلية.
- ServiceFlow: دعم عملاء بمعرفة محددة، مع اقتراح إنشاء طلب دعم داخلي بعد موافقة المستخدم.
الأسماء قوالب/قدرات فوق Runtime واحد، وليست عشرة منتجات منفصلة. لا تعِد بأن VoiceBridge أو CRM أو الدفع يعمل قبل تنفيذه.
5. البيانات والعزل والمعرفة
استخدم PostgreSQL/Supabase الحالي بتغييرات إضافية، ولا تطبق مسودة العشرين جدولًا كاملة. اقترح أقل مخطط يحقق الرحلة، بهذه الكيانات المنطقية أو مكافئها القائم:

organizations, memberships, agents, agent_versions,
knowledge_sources, knowledge_chunks, agent_version_sources,
conversations, messages, agent_runs, tool_invocations,
approvals, support_requests, usage_events.
- أضف org_id والعلاقات والقيود المناسبة؛ امنع ربط وكيل بمصدر أو محادثة من مؤسسة أخرى، حتى عند معرفة UUID صحيح. لا تثق بـorg_id المرسل من المتصفح دون فحص العضوية.
- طبق RLS وسياسات التخزين وصلاحيات RPC والجداول الجديدة، مع فحص خادمي مستقل للعمليات الإدارية. لا تستخدم SECURITY DEFINER لتجاوز العزل بلا تحقق وضبط search_path والصلاحيات.
- خزّن المسودة منفصلة عن إصدار منشور غير قابل للتعديل. اربط الإصدار بتعليماته ونموذجه وأدواته ومراجع نسخ مصادره؛ تعديل المسودة لا يغير الوكيل المنشور.
- ابدأ بإدخال نص وملفات TXT/Markdown صغيرة، مع حدود حجم ونوع معلنة وتحقق خادمي وتخزين خاص. PDF والصور والزحف العام مراحل لاحقة، لا وظائف شكلية.
- نفذ parsing وchunking وحالة معالجة واسترجاعًا حقيقيًا. المستندات بيانات غير موثوقة وليست تعليمات تمنح أدوات أو صلاحيات.
- لا تفترض أن نماذج المحادثة توفر embeddings أو أن توافق Groq مع OpenAI يعني دعم /embeddings. لا تخترع endpoint أو vectors.
- إن كانت خدمة embeddings مناسبة للعربية والإنجليزية متاحة ومفوضة، وثق النموذج والأبعاد والإصدار وسياسة إرسال البيانات واستخدمها مع pgvector. لا تشترِ مزودًا جديدًا أو تحمل نموذجًا ثقيلًا داخل Vercel تلقائيًا.
- إن لم تتوفر، ابدأ باسترجاع نصي PostgreSQL فعلي موثق كـlexical RAG، واختبر استرجاع العربية والإنجليزية. لا تسمه بحثًا دلاليًا أو vector search. افصل retrieval adapter لتبديله لاحقًا، ولا توقف باقي المنتج بسبب مفتاح إضافي غير متاح.
- الاسترجاع مقيد بمساحة العمل والوكيل والإصدار وصلاحية المصدر قبل إرسال أي نص للنموذج. كل citation يرجع إلى مقتطف مسترجع فعليًا؛ امنع روابط أو معرفات مصادر مختلقة.
- عند غياب دليل كافٍ، يوضح الوكيل عدم توفر الإجابة بدل اختلاقها. حذف المصدر يلغي وصوله فورًا وفق سياسة موثقة، بما يشمل النسخ المنشورة والـcache؛ لا تُبقِ محتواه قابلًا للاسترجاع سرًا.
6. محرك التشغيل والأدوات
أنشئ طبقات صغيرة واضحة: provider adapter، retrieval، runtime، tool registry، permissions، observability؛ استخدم المكتبات القائمة حيث تصلح ولا تنشئ framework جديدًا.
- احفظ run وحالته وإصدار الوكيل قبل الاستدعاء، وسجل النجاح/الفشل/الإلغاء وusage. احترم مهلة الاستضافة؛ لا تستمر بعمل fire-and-forget بعد انتهاء الطلب.
- التشغيل القصير يمكن تنفيذه في request مناسب؛ العمليات الطويلة تحتاج queue/worker دائمة بعد إثبات الحاجة واعتماد المورد. لا تضف تعقيدًا لا يحتاجه النطاق الحالي.
- الأدوات الأولى: knowledge_search وcreate_support_request داخلي. الثانية تكتب سجلًا حقيقيًا ظاهرًا لصاحب المساحة، ولا تدّعي اتصال Zendesk أو Salesforce.
- كل tool call يمر بتحقق schema والصلاحيات وملكية الموارد؛ النموذج لا يقرر الإذن. الإجراء الكتابي يحتاج موافقة ظاهرة مرتبطة بالمدخلات المحددة ومدة صلاحيتها، ثم تنفيذًا idempotent يمنع التكرار.
- امنع الأدوات غير المسجلة، arbitrary code execution، SQL يولده النموذج، وHTTP إلى عناوين يختارها المستخدم بلا ضوابط. لا تفعّل browser search أو code interpreter أو MCP خارجي تلقائيًا.
- لا تعِد تنفيذ إجراء ذي أثر جانبي عند إعادة الطلب أو fallback. افصل إعادة محاولة استدلال النموذج عن إعادة تنفيذ الأداة.
- اعرض نتيجة نهائية مفهومة وسجل إجراءات مختصرًا، لا تفكير النموذج الداخلي.
7. عقود API المقترحة
تحقق من المسارات الحالية وأضف ما يلزم فقط، مع توثيق auth وauthorization والمدخلات والأخطاء وidempotency. الأسماء أدناه عقود مقترحة وليست ادعاءً بأنها موجودة:

GET/POST        /api/v1/agents
GET/PATCH       /api/v1/agents/:agentId
POST            /api/v1/agents/:agentId/sources
GET/DELETE      /api/v1/agents/:agentId/sources/:sourceId
POST            /api/v1/agents/:agentId/test-runs
GET             /api/v1/runs/:runId
POST            /api/v1/runs/:runId/cancel
POST            /api/v1/approvals/:approvalId/decision
POST            /api/v1/agents/:agentId/publish
POST            /api/v1/agents/:agentId/unpublish

أضف endpoints المفاتيح أو جلسات widget في مرحلة نشرها فقط. احمِ cookies والطلبات المغيرة للحالة من CSRF وتحقق من الجلسة على السيرفر. اربط كل mutation بصلاحية واضحة؛ لا تعتبر امتلاك session إذنًا لكل وكيل.

حدّث OpenAPI وSTATUS وRESUME وWORKFLOW وتعليمات rollback لتطابق التنفيذ، دون مسح أدلة التاريخ. لا تكتب أن migrations لم تطبق إن كان السجل يثبت تطبيقها.
8. النشر والاستخدام خارج Studio
- Publish يعني تفعيل إصدار وكيل داخل منصتنا؛ لا ينشئ مشروع Vercel لكل عميل.
- ابدأ باستدعاء server-to-server بمفتاح خاص مقيد بالوكيل والصلاحية، يظهر مرة واحدة ويخزن hash له مع الإلغاء والتدوير. لا ترسله إلى JavaScript المتصفح.
- أضف widget لاحقًا في المرحلة نفسها بعد قبول API. استخدم معرف نشر علنيًا وجلسات قصيرة وحدود إساءة. CORS أو فحص Origin وحدهما ليسا مصادقة ولا حماية كاملة من إساءة الاستهلاك.
- المصادر خاصة افتراضيًا. لا ينشر widget معرفة داخلية تلقائيًا؛ يحتاج مجموعة مصادر مُعتمدة للنشر العام. لا تكشف روابط تخزين خاصة أو سجل محادثات لمستخدم آخر.
- اجعل التشغيل العام read-only أولًا؛ الأدوات الكتابية تتطلب هوية وصلاحية فعلية منفصلة.
- Unpublish وإلغاء المفاتيح يوقفان الوصول الفعلي، بما يشمل caches ذات الصلة، وليس تغيير زر في الواجهة فقط.
- جهز interface للاستحقاقات وقياس الاستخدام. لا تربط Stripe أو أي بوابة دفع الآن، ولا تصنع نجاح دفع وهميًا. الفوترة الحقيقية مرحلة منفصلة؛ لا تصفها مكتملة.
9. المراحل ونقاط التوقف
A — التصحيح المحمي:
تحقق مختصر من الحالة والفرع، صحح التوثيق المؤثر، ثم شخّص وأصلح تعتيم Hero محليًا/بمعاينة معزولة دون تغيير النصوص. سلّم diff صغيرًا وصور قبل/بعد وبصمات. توقف لاعتماد المالك.

B — الأساس وAgent Builder:
ثبت التسجيل والدخول بلا بريد، وسياسة الهوية والاستعادة، ثم مساحات العمل والوكيل المحفوظ والقالبين والإعدادات. قبول: إنشاء وكيل، الخروج والدخول، بقاء الإعدادات، ورفض وصول مستخدم آخر. توقف.

C — الذكاء والمعرفة:
صل Groq فعليًا، نفذ الاسترجاع والمحادثة والاستشهادات وسجل التشغيل، وقارن النموذجين داخليًا على حالات تمثل المنتج. قبول: إجابة مؤيدة بمصدر، امتناع عند غياب المعرفة، وعدم اختلاط المؤسسات. توقف.

D — الإجراء الحقيقي والنشر:
نفذ طلب الدعم الداخلي بالموافقة ومنع التكرار، ثم الإصدارات وAPI invocation والإلغاء، وبعد قبولها widget المقيد بمعرفة عامة معتمدة. قبول: استخدام خارج شاشة الاختبار، إصدار ثابت، ومفعول فعلي للإيقاف. توقف.

E — التسليم والاستعداد التجاري:
اجمع نتائج الاختبارات الضرورية، حالة النماذج، الفجوات المتبقية للاستعادة والفوترة والتكاملات، وخطة rollback للبيانات والكود. لا تسمّ المنتج جاهزًا للإطلاق العام مع عائق أمني معروف. Production يحتاج موافقة منفصلة تحدد البيئة.

لا تبدأ المرحلة التالية تلقائيًا. عند نقص credential أو موافقة محددة، اذكر المطلوب بدقة وأكمل فقط الأعمال المستقلة الآمنة. لا تستبدل الاتصال المفقود بـmock ثم تدّعي الإنجاز.
10. الاختبارات ومعيار التسليم
احرق Groq في تقييم جودة مفيد لا في تكرار عشوائي. حافظ على حصة Codex: اختبارات موجهة، لا بناء كامل بعد كل ملف، ولا طباعة ملفات وسجلات ضخمة.

اختبر ما يخص المرحلة فقط، مع هذه بوابات القبول:

- عزل مستخدمين/مؤسستين في الصفوف والمصادر والاسترجاع والمحادثات والتشغيل، بما في ذلك Supabase Data API وRPC حيث تتاح مباشرة.
- لا مفاتيح في المتصفح أو logs؛ ولا أسرار أو معرفة خاصة في widget.
- تقييم صغير ثابت، نحو 12 حالة عربي/إنجليزي لكل نموذج متاح: إجابة موثقة، امتناع، استخراج منظم، اختيار أداة صحيحة، ورفض تعليمات مزروعة في مستند. سجل النتائج الفعلية، ولا تستخدم حكم نموذج وحده لإثبات الأمان.
