20 أكتوبر 2026. الحالة: **VERIFIED_LOCAL / NOT_DEPLOYED_TO_PRODUCTION**. [التكليف](EXECUTION-PLAN.md)، [القرار D24](../DECISIONS.md). أذن المالك بالمتابعة بعد A، وطلب إصلاح حسابه وحذف فقرة مصادر الأصول. يستمر الفرع `codex/agynexa-studio-stage-a` و[PR #18](https://github.com/adham-younes/vzero/pull/18). لا دمج أو دفع إلى main أو Production، ولا تعديل لقاعدة قائمة أو Auth حي.

## ما يعمل في البيئة المعزولة

- `/studio` و`/ar/studio`: دخول بالحساب نفسه، إنشاء مساحة مالك واحد مرة واحدة، قائمة وكلاء، إنشاء KnowledgeGrid أو ServiceFlow، وحفظ الاسم والتعليمات واللغة والنموذج وتعديلها. الإعدادات تبقى بعد الخروج والدخول.
- العضوية قائمة على `auth.uid()` والجلسة النشطة، لا البريد أو نطاقه أو `user_metadata`. يُشتق org_id من عضوية المستخدم على الخادم؛ تمنع RLS وصول مستخدم آخر عبر التطبيق وData API. لا دعوات فرق الآن.
- إعادة إنشاء المساحة أو تكرار طلب إنشاء الوكيل لا تنتج نسخة إضافية. إرسال إعدادات مختلفة بالمفتاح نفسه يرجع 409. مراجعة المسودة تمنع الكتابة فوق تعديل أحدث بـ409؛ ليست إصدار نشر.
- صفحة الحساب تُبقي بيانات الحساب عند فشل تحميل الموجزات، وتتيح إعادة تحميلها دون ادعاء أنها فارغة. غياب الملف الشخصي المرئي للجلسة يرجع 401 لإعادة الدخول بدل 503.
- حُذفت فقرة مصادر الأصول ورابط التذييل بالعربية والإنجليزية. سجل الفيديو والترخيص باقٍ في [جرد الأصول](../content-inventory.json) و[حماية المقدمة](../baseline/hero-protection.json). الفيديو ومكوّناه وCSS إصلاح A لم تتغير في B.

اختيار النموذج محفوظ فقط. لا استدعاء Groq، ولا معرفة أو محادثة أو نشر أو تذاكر تشغيلية في B. GPT-OSS هو الإعداد الأولي؛ Qwen محفوظ للتقييم الداخلي، ولم يُختبر توافر أي منهما في هذا التسليم. المنصة لا تعرض نجاح تشغيل وهميًا.

## تشخيص شكوى الحساب وحدوده

حدد المالك الإنتاج `vzero-k0dyld6xi-adhamlouxors-projects.vercel.app`، المرتبط بالنطاق العام وmain عند `d030a60`. الفحص الحالي أعاد health=200 وجميع المفاتيح سليمة؛ الحساب دون جلسة أعاد 401. فحص قراءة فقط أثبت عدم وجود مستخدم بلا profile وقت الفحص.

ملخص سجلات Supabase بين 08:00 و10:35 UTC أظهر `/auth/v1/user` و`/rest/v1/profiles` و`/rest/v1/project_briefs` بـ200. لم يتوفر سجل طلب فاشل مطابق لشكوى المالك. موصل Vercel أعاد 404 للمشروع وللنشر المحددين؛ هذا نقص وصول في الموصل، لا دليل سقوط النشر. لذلك **السبب المحدد لرسالة المالك غير محسوم**، ولا يُنسب إلى المفاتيح.

الكود كشف مسارين يحتاجان إصلاحًا: `.single()` كان يحول غياب profile بعد نجاح Auth إلى 503، وفشل الموجزات كان يحول الحساب كله إلى حالة خطأ. عولجا واختبرا. [فحص profile](evidence/stage-b/account-diagnosis.json) حقن غياب الملف محليًا ثم أعاده: Auth=200، الاستعلام القديم=406، والمسار المصحح=401. الجلسة الملغاة المعتادة يرفضها Auth أصلًا؛ لا تُقدّم هذه الحالة كسبب مثبت للشكوى. صفحة الخطأ العامة تتيح كذلك العودة لتسجيل الدخول. نقل الإصلاح للإنتاج وإعادة التحقق على حساب المالك لم يحدثا؛ يمنع التكليف الدمج والإنتاج دون تفويض مستقل.

## البيانات والتفويض

المهاجرة الجديدة: [`20261020102401_studio_foundation.sql`](../../../supabase/migrations/20261020102401_studio_foundation.sql). تضيف `organizations` و`memberships` و`agents`، مع المفاتيح والفهارس وRLS ومنح أعمدة محددة. لا تطبيق لمسودة العشرين جدولًا ولا نقل جماعي للموجزات.

`initialize_workspace()` غلاف invoker فوق دالة خاصة ذات صلاحية definer محدودة: بلا معاملات هوية أو مؤسسة، تتحقق من user_id والجلسة، وتستخدم قفل معاملة ثم تنشئ ملكية وعضوية مرة واحدة. لا كتابة مباشرة للمستخدم على المؤسسات والعضويات. تعديل الوكيل لا يسمح بتغيير org_id أو created_by أو revision؛ trigger يحدّث المراجعة والوقت.

| SQL | البيئة المحلية | قاعدة الإنتاج xsyxvswbiptbyxyqhdim |
|---|---|---|
| حسابات `20261020074037` | طبق SQL على قاعدة اختبار جديدة | مطبق سابقًا، لم يعد تطبيقه |
| تقييد trigger المنصة `20261020074207` | لم يطبق؛ الدالة الخاصة بالاستضافة غير موجودة محليًا | مطبق سابقًا، لم يغير |
| Studio `20261020102401` | طبق SQL بمعاملة واحدة على PostgreSQL المعزول | **NOT_APPLIED** |

التطبيق المحلي مباشر عبر psql، وليس سجل migrations مستضافًا مزعومًا. أدوات الاختبار تستخدم بيانات وحسابات مصطنعة محلية فقط. إعدادات Auth الحية لم تُعدّل. حاجز `AGYNEXA_STUDIO_ENABLED=true` مطلوب لتفعيل Studio؛ غير موجود افتراضيًا، لذا لا تعتمد المعاينة على جداول لم تطبق.

## الهوية والبريد والاستعادة

يبقى Supabase Auth بالبريد وكلمة المرور، والتسجيل الخادمي يؤكد الحساب إداريًا دون رسالة. هذا **لا يثبت ملكية البريد**. مصدر الصلاحية هو العضوية المحفوظة خادميًا فقط. لا OAuth أو ربط حسابات أو دعوات تعتمد على البريد. لا مسار resetPasswordForEmail أو OTP أو magic link أو welcome email أضيف.

في اختبار Auth المحلي الحقيقي: لا تواريخ إرسال confirmation/recovery/email-change. SMTP معطل، ومزودو OAuth والربط اليدوي غير مفعّلين. هذا دليل للاختبار المحلي والكود، وليس ادعاء فحص كل إعداد إخطار في حساب Supabase المستضاف؛ لا أداة إدارة إعداداته متاحة في الجلسة.

**استعادة الحساب RELEASE_BLOCKER للاستخدام التجاري العام.** المسار المقترح للاعتماد: استعادة أصلية من Supabase يطلبها المستخدم مع بريد AGYNEXA مخصص بعد اعتماد SMTP ونطاقه واختباراته، أو هوية موثوقة يدعمها المزود. لم يُعتمد أو ينفذ أي منهما. لا دعم يعيد تعيين كلمة المرور لمجرد معرفة البريد ولا بروتوكول استعادة خاص.

## إعادة تشغيل التحقق محليًا

تعذر استخراج صورة Supabase CLI الكاملة بسبب مساحة Docker؛ استُخدمت PostgreSQL 17.11 وGoTrue 2.197.0 وPostgREST 16.4 وKong 2.8.1 الفعلية. لا mock لقاعدة البيانات أو مزود الهوية. هذه بيئة اختبار مصغرة، ولا تمثل تكافؤ جميع خدمات Supabase المستضافة أو نظام مفاتيحه الجديد؛ تستخدم JWT محلية للاختبار فقط.

من جذر المستودع، على Docker فارغ من مشروع الاختبار نفسه:

```sh
python tests/local-studio/start.py
# انتظر نجاح /auth/v1/health قبل تطبيق SQL؛ لا توجد صلة بمشروع مستضاف.
curl --fail http://127.0.0.1:54321/auth/v1/health
docker exec -i agynexa-studio-local-db-1 psql -U postgres -v ON_ERROR_STOP=1 -1 -f - < supabase/migrations/20261020074037_accounts_and_project_briefs.sql
docker exec -i agynexa-studio-local-db-1 psql -U postgres -v ON_ERROR_STOP=1 -1 -f - < supabase/migrations/20261020102401_studio_foundation.sql
docker exec agynexa-studio-local-db-1 psql -U postgres -c "NOTIFY pgrst, 'reload schema';"
node node_modules/next/dist/bin/next build
python tests/local-studio/app.py
# في terminal آخر؛ يحتاج فحص المتصفح Playwright Python وChromium.
python tests/studio-http.py /tmp/agynexa-local-status.json
python tests/studio-browser.py
python tests/account-profile-regression.py
```

الأسرار المصطنعة في `/tmp/agynexa-studio-stack` و`/tmp/agynexa-local-status.json` خارج المستودع وبصلاحيات محدودة. لا تعِد تطبيق SQL على القاعدة المحلية نفسها. لإيقافها: `docker compose -f /tmp/agynexa-studio-stack/compose.yml stop`. لا تستخدم reset/drop على مشروع مستضاف. مسار التشغيل المحلي مثبت على loopback؛ يرفض التطبيق وضع البيانات المحلي إذا كان `VERCEL` معرفًا. متغيراته خادمية `AGYNEXA_LOCAL_SUPABASE_*`، ولا تستبدل مفاتيح الإنتاج.

## التراجع والاستئناف

تراجع الكود على الفرع أو عطّل `AGYNEXA_STUDIO_ENABLED`. تحتفظ الجداول الإضافية بالبيانات؛ لا يلزم حذفها لإرجاع الموقع السابق. قبل تطبيق مستضاف مستقبلًا يلزم تفويض المشروع والإجراء، نسخة احتياطية مناسبة وفحص استعادة، ثم migration وتحقق بعزل المستخدمين. rollback الكود ليس rollback للبيانات.

الخطوة التالية **C بعد قبول B**: التحقق من Groq والموديلين، مصادر نصية خاصة واسترجاع PostgreSQL lexical وإجابات بمصادر وسجل تشغيل. لا تبدأ D أو widget تلقائيًا. تفعيل قاعدة مستضافة أو نشر إصلاح الحساب إلى الإنتاج طلبان مستقلان وفق التكليف؛ لم يفعلا ضمن هذه المرحلة.

مراجع التنفيذ التي روجعت: [Supabase SSR sessions](https://supabase.com/docs/guides/auth/server-side/advanced-guide)، [RLS والمنح](https://supabase.com/docs/guides/database/postgres/row-level-security)، وسجل تغييرات Supabase بتاريخ الفحص. مرجع Next Route Handlers قُرئ من docs المرفقة بالإصدار المثبت.
