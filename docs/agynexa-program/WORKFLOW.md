# سير العمل والتوثيق والنشر

## الاستئناف

تمت [مطابقة مراجعة السوق بالكود والخطة](reviews/MARKET-REVIEW-RECONCILIATION-2026-10-19.md). لا يُعتمد اقتراح RFQ أو مراحل A–D بديلًا للخطة الأصلية. التكليف الحالي هو [Agent Studio، المرحلة A فقط](agent-studio/README.md)، مع توقف للاعتماد. تفويضات النشر السابقة لا تنطبق عليه.

1. اقرأ [RESUME](RESUME.md)، [STATUS](STATUS.json)، [BACKLOG](BACKLOG.md)، ثم تعليمات المالك الأحدث.
2. افحص `git status --short --branch` و`git fetch origin` وسجل `origin/main`. لا تفترض أن الفرع المحلي أو آخر نشر مذكور ما زال الأحدث.
3. حدّد المطلوب في بند واحد أو نطاق محدود، واربطه بمرحلة أو معرف backlog. لا تعاود البحث المرجعي الشامل.
4. اقرأ الملفات المتأثرة و[DESIGN](../../DESIGN.md) عند تعديل الواجهة، و[حالة APIs](architecture/API-STATUS.md) عند تعديل وظيفة.
5. حافظ على تغييرات المستخدم غير المسجلة. اعمل على فرع مناسب دون force-push أو إعادة كتابة تاريخ مشترك.

## موارد التصميم المتصلة

قبل بدء إعادة تنظيم صفحة أو إعداد صور ومكونات، راجع [قائمة الموصلات التي أكدها المالك](CONNECTED-DESIGN-TOOLS.md). اختبر القدرة المطلوبة في الاتصال الصحيح، ثم سجل مصدر الأصل وحق الاستخدام وموضعه ودليل مراجعته. هذا الجرد أحدث من جرد أدوات المرحلة 0؛ لا يثبت وحده دمج الموصلات في runtime الموقع.

## دورة التغيير

نطاق واضح → كود/محتوى → فحص مناسب → توثيق الحالة والقيود → commit → push/PR → تحقق الدمج → نشر إن كان مفوضًا → دليل من الإصدار الفعلي.

لا تكفي نتيجة محلية لإعلان نجاح الإنتاج. نجاح فحص الاتصال لا يثبت وظائف الوكلاء. الحسابات والموجزات وRLS منفذة وفق دليلها؛ وظائف Studio لم تبدأ.

## التشغيل المحلي

من جذر المستودع، استخدم نسخة pnpm المحددة في package.json:

```bash
pnpm install --frozen-lockfile
pnpm dev --port 3011
```

لفحص نسخة البناء، أوقف dev ثم:

```bash
pnpm build
pnpm start --port 3011
```

الخادم يبقى في طرفية مستقلة أثناء فحص HTTP. الصفحات وواجهتا الأعمال الأصليتان لا تحتاج مفاتيح. فحص اتصال Supabase يحتاج متغيرات URL وpublishable وsecret المذكورة في TECHNICAL-PLAN؛ دونها يعيد 503 صادقًا. لا تضع بيانات فعلية في الأمثلة أو الاختبارات.

## سياسة الفحوص بحسب المخاطرة

| نوع التغيير | الفحص المناسب |
|---|---|
| توثيق فقط | `python3 docs/agynexa-program/tools/verify-docs.py`، مراجعة النص و`git diff --check`؛ لا build/lint/test للتطبيق |
| نصوص أو UI | فحص الصفحات المتأثرة، سطح مكتب وعينة عربية ضيقة، روابط وRTL وfocus؛ build عند تغير الكود/المكونات |
| API/حسابات | اختبارات وحدات وحدود HTTP لكل handler متغير؛ حالات النجاح والرفض وآثار التخزين/الإرسال إن وجدت |
| CSS مشترك أو Hero | تحقق البصمات واللون وoverlay والتشغيل والمقاسات؛ لا يكفي ثبات ملف الفيديو وحده |
| إصدار منتج | build/TypeScript مرة واحدة، فحوص HTTP ممثلة، تفاعل فعلي، وسجل البيئة/commit/URL؛ أعد فقط ما تبرره إصلاحات لاحقة |
| DB/صلاحيات | توجد أدلة سابقة لعزل الحسابات وإبطال الجلسة. أي توسع يحتاج بيئة معزولة وفحوص الدور والعزل والتكرار والاستعادة؛ الاستعادة الكاملة غير متحققة |

أوامر الفحوص الموجودة:

```bash
node --experimental-strip-types --test tests/procurement.test.mjs
node tests/http-smoke.mjs http://localhost:3011
```

فحص الموقع السابق: 4 اختبارات وحدات و28 فحص HTTP تشمل 15 صفحة. تسليم الحسابات الأحدث: 10 وحدات و22 فحص HTTP إنتاجي واختبار RLS ورحلة جوال؛ راجع [الدليل](evidence/accounts-2026-10-20/verification.json). لا تعاد اختبارات التسجيل الحي لمجرد تعديل توثيق أو CSS. أداة smoke ترسل فقط بيانات عددية افتراضية إلى مثال المشتريات؛ لا بريد أو دفع أو تخزين. لا توجد مهمة ESLint، فلا تسجل نجاح lint غير منفذ. لا تحول الفحص الكامل إلى شرط لكل تعديل صغير.

تحقق حماية الملفات عند تعديل منتج يؤثر عليها:

```bash
shasum -a 256 public/videos/background.mp4 @components/landing-5-hero-video.tsx @components/landing-5-hero-section.tsx
```

قارن بالقيم في [دليل الحماية](evidence/README.md). الملفات المشتركة مثل CSS وShell تحتاج فحصًا بصريًا أيضًا.

## GitHub وVercel

المستودع `adham-younes/vzero`، والفرع الإنتاجي `main`، والمشروع `vzero` ضمن `adhamlouxors-projects`. فرع غير إنتاجي يمكن أن ينتج Preview، ودمج `main` يمكن أن ينتج نشرًا إنتاجيًا تلقائيًا حتى لو كان التغيير توثيقًا فقط.

1. اعرض diff وحدود التغيير قبل commit؛ لا ترفع `.env` أو `.vercel` أو node_modules أو سجلات خاصة.
2. ارفع الفرع وأنشئ PR يصف المشكلة والنتيجة والفحوص والقيود وروابط التوثيق. عند استخدام Codex أرفق PR بالمهمة عبر أداة إرفاقه.
3. افحص حالة PR وفحوصه. لا تتجاوز فحصًا فاشلًا. وجود خيار Allow auto-merge في إعدادات GitHub لا يعني تفعيله لكل PR.
4. عند تفويض الدمج/النشر، ادمج HEAD الذي راجعته وتحقّق من SHA الدمج. لا تنشئ نشرًا يدويًا ثانيًا إذا كانت Git Integration قامت به.
5. راقب النشر المطابق للمصدر باستخدام اللوحة أو CLI؛ `Ready` و`target: production` وalias الصحيح أدلة مختلفة يجب تمييزها.
6. لتغيير المنتج، اختبر النطاق العام والرحلة المتأثرة فعليًا. لتوثيق فقط، تحقق من وجود المستندات على `main` وعدم تغير ملفات المنتج؛ لا تعد فحوص التطبيق دون سبب.

أوامر قراءة مفيدة لا تغيّر الإعدادات:

```bash
gh pr view NUMBER --json state,headRefOid,mergeCommit,statusCheckRollup,url
vercel inspect https://vzero-nine-beryl.vercel.app --scope adhamlouxors-projects
git log -5 --oneline origin/main
```

استبدل `NUMBER` برقم PR الفعلي. لا تُظهر رموز دخول أو متغيرات بيئة في السجل. إذا تعذر موصل، استخدم البديل الموثق المتاح ولا تغيّر SSO أو الحماية.

## ما الذي يوثّق مع كل تسليم؟

- `STATUS.json`: الحالة الحالية، آخر إصدار منتج متحقق منه، الفحوص وحدودها، والخطوة التالية.
- `STAGE-MATRIX.md` و`BACKLOG.md`: ما أُقفل وما بقي، دون إعادة وصف المقترح على أنه منفذ.
- `TECHNICAL-PLAN.md`، `current-routes.json` و`architecture/current-api.openapi.json`: عند تغير الكود أو المسارات أو العقد.
- `releases/`: تقرير بتاريخ وcommit وURL ونتائج الفحوص الفعلية. التقارير السابقة تبقى تاريخية.
- `evidence/`: لقطات ونتائج قابلة للوصول من GitHub، مسماة بالبيئة والإصدار؛ دون بيانات حساسة.
- `DECISIONS.md`: تغيير نطاق/تفويض/قرار يفسر الاختلاف عن الخطة.
- `RESUME.md`: نقطة دخول قصيرة تحدد الملفات والخطوة التالية دون إعادة بحث.

لا تكتب SHA توثيق ذاتيًا داخل نفس commit؛ استخدم `git log` أو PR لتحديد commit المستند، واحتفظ بمعرّف إصدار المنتج منفصلًا. إذا ولّد دمج توثيق نشرًا جديدًا بنفس المنتج، سجله كتغيير توثيق عند الحاجة، ولا تدّع أنه إصدار وظائف جديد.

## التراجع

1. حدد سبب التراجع والإصدار المتضرر. تأكد من تفويض إجراء تغيير الإنتاج.
2. اختر إصدارًا متحققًا من [RELEASES](RELEASES.md)، وليس «آخر رابط» دون مصدر معروف.
3. استخدم عملية Rollback/Promote المدعومة في Vercel للإصدار المختار. لا تغيّر الأسرار أو النطاقات أو قواعد الحماية لتسهيل التراجع.
4. أعد فحص target وaliases والموقع والرحلة المتأثرة. `Ready` وحده لا يكفي.
5. عالج Git لاحقًا بـrevert للمصدر المعني حسب الحاجة حتى لا يعيد الدفع التالي الكود المعيب؛ لا force-push إلى main.
6. سجل السبب والوقت وSHA ومعرّف النشر والنتيجة. مهاجرتا `20261020074037` و`20261020074207` مطبقتان في مشروع الحسابات. تراجع الكود لا يلغي مخطط قاعدة البيانات أو بياناته.
7. لتراجع إصدار الحسابات، احتفظ بالجداول والبيانات وحدد توافق إصدار التطبيق المستهدف معها. لا تستخدم DROP أو reset أو migration عكسية مدمرة. أي تغيير قاعدة قائمة يحتاج تفويض المشروع والإجراء وخطة نسخ/استعادة؛ لا يوجد دليل اختبار استعادة كاملة حاليًا.
8. المرحلة A محلية/معاينة فقط: يعكس commit إصلاح CSS وحده عند الحاجة، ولا يلزم إجراء قاعدة بيانات. لا تنفذ تراجع إنتاج أو ترويج معاينة ضمن تفويض A.
